# Changelog

All notable changes to the Cloud Network Assessment AWS Appliance are documented in
this file. Application changes are recorded in the core repository's `CHANGELOG.md`; this file
covers deployment, operations and this repository itself.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **MCP and draw.io endpoints reach the web tier** (`TODO.md` → T-113). Both workload roots gain the five variables the Azure sibling's roots already had — `azure_mcp_endpoint`, `azure_mcp_transport` (default `streamable-http`), `aws_mcp_endpoint`, `aws_mcp_transport` (default `streamable-http`) and `drawio_mcp_url` — and pass them to the web container as `CNA_AZURE_MCP_ENDPOINT`, `CNA_AZURE_MCP_TRANSPORT`, `CNA_AWS_MCP_ENDPOINT`, `CNA_AWS_MCP_TRANSPORT` and `CNA_DRAWIO_MCP_URL`, exactly as Azure does. All five are optional and default to the app's own fallbacks (offline recommendation library, `localhost` draw.io), so an existing plan is unchanged until a value is supplied. `README.md` already listed the matching `CNA_*` repository variables; `210-deploy` will pass them with `-var` once it has a real `terraform plan` step (T-101). Cloud-specific Terraform only — no sibling change.
- **Image-update check contract for the web tier** (core `CHANGELOG.md` → Unreleased, Admin → Updates). Both workload roots inject `CNA_WEB_IMAGE` (the deployed web image reference), `CNA_IMAGE_REGISTRY_USERNAME`, `CNA_APPLIANCE_REPO` (`github_owner/github_repository`) and, as a secret-backed variable, `CNA_IMAGE_REGISTRY_TOKEN` from the `password` key of the Docker Hub Secrets Manager secret ECS pulls with — the same pull-only credential, no new GitHub secret or variable. The web tier uses them to compare its running build with the newest published build in the registry and to link to this repository's `230-image-update` and `210-deploy`. Mirrored in the sibling appliance.
- **Deployment-side backlog transferred from the core** (core `TODO.md` T-507, 2026-09-15). The core removed its copy of the deployment layer (core T-504) and handed over every item that describes this repository's Terraform and workflows: `TODO.md` T-104 – T-110 (deploy-role ARN consumption, platform and workload root applies, Bedrock model ids, parity verification, Route 53 + ACM validation, drift-check visibility) and `REVIEW.md` R-008 (runtime secrets have no defaults). T-111 carries the 27 Terraform findings the core's production-readiness review engine had recorded for the AWS modules — 21 audit/verified-compliant records and the six gated escalations now owned by R-001 – R-005 and R-008 — with paths rebased to `infra/terraform/modules/`. `scripts/validate_documentation_model.py` picks up the core's `.kiro/` exclusion so the two copies stay identical.
- **Initial import from the core repository** (`saulpatinojr/Work-Cloud_Network_Assessment` at `1951830`). The AWS Terraform (`infra/terraform/providers/aws/*` → `infra/terraform/modules/*`, `infra/terraform/environments/aws/{dev,prod}` → `infra/terraform/environments/{dev,prod}`), the deploy and operations workflows (`000`, `100`, `211`/`212` → `210-deploy`, `220`, `320`, `330`, `340`, `350`, `360`), the CI evidence scripts and the release catalog were cut from the core so that customers see one cloud per repository. Module sources were rewritten to the new layout; nothing else in the Terraform changed. `320-publish-portal` lost its `cloud` input — this appliance publishes to Amazon S3 only.
- **`230 · Image Update`.** Listens for the core's `cna-image-published` dispatch and polls the core's build manifest every six hours; auto-deploys `dev` through `210` with the recorded `ai_mode`, and opens an `update-available` issue for `prod`. Never touches an environment that has not been deployed once.
- **`300 · Validate`.** This repository's CI: `detect-secrets` (gating), the documentation-model guard, and `terraform fmt` / `terraform validate` on all four roots.
- `README.md` (the intro page), `CLAUDE.md` (agent rules: app code lives in the core; every structural change is mirrored to the sibling appliance), `REVIEW.md`, `TODO.md`, and the `update-available` issue template.
- `000`, `100`, `220`, `330`, `340`, `350` and `360` are fail-fast scaffolds with the same inputs as the Azure appliance; `210-deploy` is the core's `212` scaffold renamed. All of them point at `REVIEW.md` R-001 – R-003 and `TODO.md` T-101 / T-102.

### Changed
- **The core is now `Work-Cloud_Network_Core`** (core `TODO.md` T-509, 2026-09-18). The application code and the image builds moved from the project's original repository, `Work-Cloud_Network_Assessment`, into a dedicated internal core repository; the original is archived. `CLAUDE.md` and `README.md` point at the new repository and its Wiki, and the `CORE_REPO` variable — the only place `230-image-update` learns where the build manifest lives — must be set to the new name by the repository admin (`REVIEW.md` R-009). Nothing else changes: the image tag scheme, the manifest schema, the `cna-image-published` dispatch and the runtime environment contract are the same, so a deployed environment is unaffected. Mirrored in the sibling appliance in the same change set.
- **Every workflow runs on GitHub-hosted runners (`ubuntu-latest`).** `300 · Validate` moved first (its jobs need no cloud credentials, and a new repository had no runner registered, which left the first pull request's checks queued indefinitely); the deploy and operations workflows — `000`, `100`, `210`, `220`, `230`, `320`, `330`, `340`, `350`, `360` — follow now that the self-hosted runner the original repository used is retired. Nothing in them needs a private network: cloud access is OIDC, and the real jobs (`230`, `300`, `320`) use only GitHub, Docker Hub and the AWS APIs; the scaffolds keep the same `runs-on` so they fail on their own message, not on a missing runner. `scripts/bootstrap-runner.sh` (the VPS runner provisioner) and its `.secrets.baseline` entry are removed. Mirrored in the sibling appliance.

### Removed
- **Two Azure-only CI scripts that had been copied here** — `scripts/ci/approve_frontdoor_private_link.sh` and `scripts/ci/detect_alz_diagnostic_policies.sh` (Azure Front Door private-link approval and Azure Landing Zone diagnostic-policy detection). No AWS workflow ever called them and `CLAUDE.md` forbids Azure content in this repository; they were carried over with the rest of `scripts/ci/` when the deployment layer was cut from the original repository. Found by the repository-split validation of 2026-09-22, which rebuilt the original repository's trees from the history the core imported (its final state, `5d3b914`, and the state just before the deployment layer was removed, `8bb989d`) and compared every one of the 214 files that left the core against the `main` branch of the core and both appliances: all application code is in the core, all 60 AWS Terraform files are here (56 byte-identical, 4 differing only in the rewritten module `source` paths and the later image-update change), the `211`/`212` deploy workflows became each appliance's `210`, the release catalog moved intact to the Azure appliance, and nothing points at a path that no longer exists. Three pre-existing gaps the same validation recorded are tracked, not fixed, here: the operational workflows are still fail-fast scaffolds (`TODO.md` T-101 / T-102, `REVIEW.md` R-001 – R-003), this repository has no bootstrap or scanner-account scripts (`TODO.md` T-112), and the workload roots do not inject the MCP and draw.io endpoints the Azure roots do (`TODO.md` T-113). The original repository, `Work-Cloud_Network_Assessment`, stays archived: the validation read only the imported history and opened nothing there. Commits made in the archive after `5d3b914` (2026-09-15) and before it was archived (2026-09-18) were not reachable from this session and are not covered.
