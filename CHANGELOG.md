# Changelog

All notable changes to the Cloud Network Assessment AWS Appliance are documented in
this file. Application changes are recorded in the core repository's `CHANGELOG.md`; this file
covers deployment, operations and this repository itself.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **Edge access logging** (`TODO.md` → T-111, `terraform-aws:edge-access-logging`). The storage module gains a `<prefix>-logs-<hex>` bucket — SSE-S3, versioned, public access blocked, objects expiring after `log_retention_days`, ACLs left enabled because CloudFront standard logging delivers through the `awslogsdelivery` bucket ACL — and the security module writes CloudFront standard logs to it under `cloudfront/` (cookies excluded) and the WAF web ACL's logs to a us-east-1 CloudWatch log group `aws-waf-logs-<prefix>` with the `cookie` and `authorization` headers redacted, so edge traffic and blocked requests are auditable without a session token ever landing in a log line. Both are behind the roots' `enable_edge_logging` (default `true`); the log group uses the CloudWatch service key because the platform's customer-managed key lives in the deployment region and cannot encrypt a us-east-1 group. New workload outputs `logs_bucket` and `waf_log_group_name`; `330`'s pre-destroy bucket emptying includes the `-logs-` prefix. Cloud-specific Terraform and the AWS-only destroy step — no sibling change.
- **RDS observability options** (T-111, `terraform-aws:rds-observability-options`). The database module takes `performance_insights_enabled` (encrypted with the platform KMS key, 7-day retention by default), `monitoring_interval` (a non-zero value creates the `<prefix>-rds-monitoring` role with `AmazonRDSEnhancedMonitoringRole` and turns enhanced monitoring on) and `iam_database_authentication_enabled`, surfaced on the roots as `db_performance_insights_enabled`, `db_monitoring_interval` and `db_iam_authentication_enabled`. Prod enables Performance Insights and 60-second enhanced monitoring; dev enables neither; IAM authentication is off in both because the application connects with `DATABASE_URL`.
- **The seven operational workflows are real** (`TODO.md` → T-102): `000 · Bootstrap Backend`, `100 · Validate Prerequisites`, `220 · Fast Redeploy`, `330 · Teardown Platform`, `340 · Sync Local Keys`, `350 · Drift Detection · dev` and `360 · Drift Detection · prod` replace their fail-fast scaffolds with the Azure sibling's job shape, step for step, on unchanged inputs. `000` creates and hardens the state bucket (versioning, SSE-KMS, public access blocked), creates the `LockID` lock table, initialises the platform state and confirms the `TFSTATE_*`/`AWS_REGION*` variables — idempotent against what `scripts/Initialize-CnaAwsGitHubSecrets.ps1` already made. `100` checks the secrets and variables the README table lists (`CNA_ENTRA_TENANT_ID` included), probes that the Entra client id still exists, checks Docker Hub pull access, assumes the deploy role and verifies its reader and deploy-write policies, the state backend and Bedrock model access (R-005, the AWS twin of Azure's provider-registration check). `220` rolls one or more ECS services to a new image with `scripts/ci/ecs_update_image.sh` (a new task-definition revision from the current one, tagged so the deploy role's tag-scoped ECS permissions apply, then a forced deployment) and probes `/api/health` through CloudFront. `330` keeps the safety gates, then — AWS having no resource group to delete — runs a real `terraform destroy`, workload then platform, after forgetting the deploy identity in state (so the destroy cannot delete the role it runs as), lifting RDS deletion protection and emptying the versioned buckets; it clears both state objects, previews and optionally deletes tagged leftovers, force-deletes secrets still in their recovery window (the twin of Azure's soft-delete purge) and, on request, removes the backend — refusing while the other environment still has state in the shared bucket. `340` reads the four Secrets Manager secrets plus the Bedrock contract values from the api task definition into a 1-day `.env` artifact; there is no firewall window to open or close. `350`/`360` plan both roots with `-detailed-exitcode` against the images and `ai_mode` recorded in the release catalog, warn on drift, and — unlike the Azure versions — fail when the plan itself errors; `350`'s daily schedule is present but commented out until dev has been deployed once. Authored and validated (YAML, every `run` block under `bash -n`, yamllint, every action SHA-pinned, `terraform validate`), not yet run.

### Changed
- **The X-Ray daemon sidecar is pinned** (T-111, `terraform-aws:xray-sidecar-latest-tag`): `public.ecr.aws/xray/aws-xray-daemon:3.7.0` through the compute module's new `xray_daemon_image` variable, whose validation rejects `:latest` and untagged references, so a task-definition rebuild can no longer change the running daemon silently. Bump the default deliberately.
- **The two ECR interface endpoints are off by default** (T-111, new finding `terraform-aws:ecr-endpoints-unused`). Both platform roots gain `enable_ecr_endpoints` (default `false`) gating `ecr.api` and `ecr.dkr`: the appliance pulls its images from Docker Hub and the X-Ray daemon from ECR Public, neither of which a private ECR endpoint serves, so the pair was an hourly charge per AZ that carried no traffic. The default platform now creates seven endpoints; `TODO.md` → T-105 records the change. Enable the variable only if the images are ever mirrored into a private ECR registry.
- **The deploy-write IAM policy allows `dynamodb:CreateTable`, `DescribeTable` and `TagResource`** on top of the state-lock item actions, so `000` can create the lock table under CI; `DeleteTable` is deliberately absent — the table outlives every environment and only an account admin removes it. The bootstrap script's inline copy matches.

### Shared change the sibling still needs

The AWS versions fail on it; the same two-line fix belongs in the Azure appliance's `350-drift-dev.yml` and `360-drift-prod.yml` (its `TODO.md` → T-105 territory). Recorded here per `CLAUDE.md` because this change set opens no sibling PR for it.
- **`210 · Deploy` is a real release workflow** (`TODO.md` → T-101). The fail-fast scaffold is replaced by the Azure sibling's four jobs, step for step, with the same inputs, artifacts and release-catalog contract: `policy-gates` (Docker Hub defaults and pull check, `terraform fmt`/`init`/`validate` on both roots, a curated Checkov gate of 22 `CKV_AWS_*`/`CKV2_AWS_*` checks chosen from a scan of the roots so it blocks regressions rather than day one, a read-only Bedrock model-access warning for `saas`), `plan` (SHA-pinned images from `latest-build.json`, GitHub App token, platform plan, workload plan with the platform outputs passed as `-var` — the AWS roots take `vpc_id`, subnet and security-group ids as variables where Azure uses data sources — and the deployment manifest), `apply` (under `hub` for prod: platform apply, post-platform workload re-plan and apply, `aws rds wait db-instance-available`, the database migration as a one-off Fargate task registered from the api task definition with the migrator image and only `DATABASE_URL` from its secrets, an ECS service roll — dev services asleep at scale-to-zero are woken to one task for verification — the NextAuth redirect-URI report against the CloudFront domain, and the apply evidence) and `verify` (reachability poll on the CloudFront domain, ALB target-group healthy percentage written in the Azure Monitor shape `evaluate_deployment_evidence.py` already reads, non-blocking CloudWatch success-rate telemetry, CloudFront distribution state as the promotion record, ACM expiry when `CNA_ALB_CERTIFICATE_ARN` is set, evidence evaluation, catalog persist/commit/push, provenance artifact). Cloud swaps only: `aws-actions/configure-aws-credentials` with `AWS_DEPLOY_ROLE_ARN`, the S3/DynamoDB backend with `<env>/{platform,workload}.tfstate` keys, `TF_VAR_db_admin_password` / `TF_VAR_dockerhub_token` in place of the Azure names, `saas ⇒ bedrock` for `ai_engine_default`, and no Key Vault/storage firewall windows or private-link approval (IAM-gated services need none). New repository variables: `CNA_ENTRA_TENANT_ID` (AWS has no Azure OIDC secret to read the tenant from), optional `AWS_TARGET_ACCOUNT_ID` and `CNA_ALB_CERTIFICATE_ARN`. Every action is SHA-pinned, including `actions/create-github-app-token`. Authored and validated (YAML, every `run` block under `bash -n`, `terraform validate` on all four roots, the Checkov gate green on dev and prod), not yet run — there is no account (`REVIEW.md` R-001); the first live run is T-108's.
- **`scripts/ci/update_apply_evidence.py` records a cloud-neutral `edge_host_name`** (Front Door endpoint on Azure, CloudFront domain on AWS) beside the existing Azure keys, plus `cloudfront_distribution_id`, `ecs_cluster_name`, `alb_dns_name`, `db_address` and `artifacts_bucket` when set; an Azure run's output is unchanged apart from the added key. ### Fixed
- **The deploy-write IAM policy now allows `bedrock:*`, `sns:*` and `xray:*`** (T-111, the account-independent part of `terraform-aws:gated:oidc-role`). The stack creates a Bedrock inference profile (and an optional guardrail), an SNS alarm topic and an X-Ray sampling rule, but only the bootstrap script's inline copy of the policy allowed them; once `terraform import` hands the role to Terraform and the managed policy replaces that copy, the very next `210` apply would have failed on the first of them. The module and the script's copy carry the same action list again. The wider tightening to concrete resource ARNs stays gated on the first live account (`REVIEW.md` R-003).
- **The deploy-write IAM policy denied every ECS create and describe call.** `modules/identity` scoped `ecs:*` by `aws:ResourceTag/Project`, but a create call has no resource tag yet (IAM evaluates `aws:RequestTag` there) and `Describe*`/`List*` carry no resource, so the first `terraform apply` and `210`'s migrator `run-task` would both have failed with AccessDenied. Split into `ECSCreateTagged` (`CreateCluster`, `CreateService`, `RegisterTaskDefinition`, `RunTask`, `TagResource` with `aws:RequestTag/Project`), `ECSRead` (`Describe*`, `List*`, `DeregisterTaskDefinition`) and the unchanged tag-scoped `ecs:*` for mutations. The bootstrap script's inline copy carries the same three statements. Found while authoring T-101; the wider least-privilege tightening stays T-111.
- **AWS bootstrap and scanner-account scripts** (`TODO.md` → T-112), the counterparts of the Azure appliance's `Initialize-CnaGitHubSecrets.ps1` and `New-CnaAssessmentServicePrincipal.ps1`. `scripts/Initialize-CnaAwsGitHubSecrets.ps1` creates, idempotently and under the operator's `aws` and `gh` sessions, everything `REVIEW.md` R-001 – R-003 ask a human for: the GitHub OIDC provider, the environment's `<project>-<env>-<region_short>-github-deploy` role with the identity module's exact trust policy (so `terraform import` adopts it drift-free — the script prints the five import commands), its three reader policies and an inline bootstrap copy of the module's deploy-write policy for the first apply (removed again with `-RemoveBootstrapPolicy` once Terraform's managed policy is attached; it also names `bedrock`, `sns` and `xray`, which the stack creates and the module's policy does not yet allow), the versioned SSE-KMS public-access-blocked state bucket and `LockID` lock table, the `dev`/`prod`/`hub` environments, the `AWS_DEPLOY_ROLE_ARN` secret and the `TFSTATE_BUCKET`, `TFSTATE_LOCK_TABLE`, `AWS_REGION`, `AWS_REGION_SHORT` variables. `scripts/New-CnaAwsAssessmentRole.ps1` creates the read-only scanner role the app's "Add Cloud Connection" form asks for — trust limited to one principal with an `sts:ExternalId` condition, `ReadOnlyAccess` + `SecurityAudit` + `AWSBillingReadOnlyAccess` — in the management account and, with `-OrganizationWide`, in every member account through a service-managed, auto-deploying CloudFormation StackSet so the same role name exists everywhere discovery assumes it; `-CreateScannerUser` adds the least-privilege IAM user (assume that role, list accounts, describe regions) and mints the access key the form needs, printed once and never stored. Neither script writes a credential to disk; the JSON run reports go to the gitignored `.reports/`. Cloud-specific scripts only — no sibling change.
- **MCP and draw.io endpoints reach the web tier** (`TODO.md` → T-113). Both workload roots gain the five variables the Azure sibling's roots already had — `azure_mcp_endpoint`, `azure_mcp_transport` (default `streamable-http`), `aws_mcp_endpoint`, `aws_mcp_transport` (default `streamable-http`) and `drawio_mcp_url` — and pass them to the web container as `CNA_AZURE_MCP_ENDPOINT`, `CNA_AZURE_MCP_TRANSPORT`, `CNA_AWS_MCP_ENDPOINT`, `CNA_AWS_MCP_TRANSPORT` and `CNA_DRAWIO_MCP_URL`, exactly as Azure does. All five are optional and default to the app's own fallbacks (offline recommendation library, `localhost` draw.io), so an existing plan is unchanged until a value is supplied. `README.md` already listed the matching `CNA_*` repository variables; `210-deploy` will pass them with `-var` once it has a real `terraform plan` step (T-101). Cloud-specific Terraform only — no sibling change.
- **Image-update check contract for the web tier** (core `CHANGELOG.md` → Unreleased, Admin → Updates). Both workload roots inject `CNA_WEB_IMAGE` (the deployed web image reference), `CNA_IMAGE_REGISTRY_USERNAME`, `CNA_APPLIANCE_REPO` (`github_owner/github_repository`) and, as a secret-backed variable, `CNA_IMAGE_REGISTRY_TOKEN` from the `password` key of the Docker Hub Secrets Manager secret ECS pulls with — the same pull-only credential, no new GitHub secret or variable. The web tier uses them to compare its running build with the newest published build in the registry and to link to this repository's `230-image-update` and `210-deploy`. Mirrored in the sibling appliance.

### Changed
- **The core is now `Work-Cloud_Network_Core`** (core `TODO.md` T-509, 2026-09-18). The application code and the image builds moved from the project's original repository, `Work-Cloud_Network_Assessment`, into a dedicated internal core repository; the original is archived. `CLAUDE.md` and `README.md` point at the new repository and its Wiki, and the `CORE_REPO` variable — the only place `230-image-update` learns where the build manifest lives — must be set to the new name by the repository admin (`REVIEW.md` R-009). Nothing else changes: the image tag scheme, the manifest schema, the `cna-image-published` dispatch and the runtime environment contract are the same, so a deployed environment is unaffected. Mirrored in the sibling appliance in the same change set.
- **Every workflow runs on GitHub-hosted runners (`ubuntu-latest`).** `300 · Validate` moved first (its jobs need no cloud credentials, and a new repository had no runner registered, which left the first pull request's checks queued indefinitely); the deploy and operations workflows — `000`, `100`, `210`, `220`, `230`, `320`, `330`, `340`, `350`, `360` — follow now that the self-hosted runner the original repository used is retired. Nothing in them needs a private network: cloud access is OIDC, and the real jobs (`230`, `300`, `320`) use only GitHub, Docker Hub and the AWS APIs; the scaffolds keep the same `runs-on` so they fail on their own message, not on a missing runner. `scripts/bootstrap-runner.sh` (the VPS runner provisioner) and its `.secrets.baseline` entry are removed. Mirrored in the sibling appliance.

### Removed

No AWS workflow ever called them and `CLAUDE.md` forbids Azure content in this repository; they were carried over with the rest of `scripts/ci/` when the deployment layer was cut from the original repository. Found by the repository-split validation of 2026-09-22, which rebuilt the original repository's trees from the history the core imported (its final state, `5d3b914`, and the state just before the deployment layer was removed, `8bb989d`) and compared every one of the 214 files that left the core against the `main` branch of the core and both appliances: all application code is in the core, all 60 AWS Terraform files are here (56 byte-identical, 4 differing only in the rewritten module `source` paths and the later image-update change), the `211`/`212` deploy workflows became each appliance's `210`, the release catalog moved intact to the Azure appliance, and nothing points at a path that no longer exists. Three pre-existing gaps the same validation recorded are tracked, not fixed, here: the operational workflows are still fail-fast scaffolds (`TODO.md` T-101 / T-102, `REVIEW.md` R-001 – R-003), this repository has no bootstrap or scanner-account scripts (`TODO.md` T-112), and the workload roots do not inject the MCP and draw.io endpoints the Azure roots do (`TODO.md` T-113). The original repository, `Work-Cloud_Network_Assessment`, stays archived: the validation read only the imported history and opened nothing there. Commits made in the archive after `5d3b914` (2026-09-15) and before it was archived (2026-09-18) were not reachable from this session and are not covered.
