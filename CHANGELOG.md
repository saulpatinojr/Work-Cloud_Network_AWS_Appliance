# Changelog

All notable changes to the Cloud Network Assessment AWS Appliance are documented in
this file. Application changes are recorded in the core repository's `CHANGELOG.md`; this file
covers deployment, operations and this repository itself.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed
- **Images are deployed by digest** (core `TODO.md` → T-701; v1.0 review findings RELEASE-001 / IMG-012). `230-image-update` now requires the core manifest's `digests{}` and composes the pinned reference `docker.io/<ns>/cna:<role>-sha-<7>@sha256:<digest>` for the api, worker, web and migrator images — the tag stays for people and for the web tier's image-update check, the digest is what the platform pulls — and passes all four to `210` (new `migrator_image` input). A manifest without `digests{}` fails the update with a message to rebuild the core first. `210-deploy` refuses any empty or floating (`*-latest`) reference, drops the `migrator-latest` default and the never-working "resolve from the appliance's own build manifest" step, validates every image input with one shared `validate_image_ref` function (pinned accepted, tag-only accepted with a warning, anything else refused), and records the pinned references in the release catalog. Rollback takes `previous_migrator_image` through `workflow_call`; a dispatch rollback resolves the migrator from the catalog record that matches `previous_api_image` (GitHub caps `workflow_dispatch` at ten inputs). `220-fast-redeploy` applies the same validation; `350`/`360` no longer fall back to floating tags when the catalog has no image (they fail instead); `100-validate-prereqs` checks Docker Hub pull access with an authenticated tags listing rather than by pulling `*-latest`. Terraform image variables lose their `example-namespace/*-latest` module defaults and document the pinned form. Shared change — `230`, `resolve_rollback_target.py`, `validate_image_ref` and the `update-available` issue template are byte-identical in the sibling appliance.

### Security
- **The API is no longer reachable from the internet, and it now requires a token** (v1.0 review findings SEC-001 / NET-AWS-003 / NET-AWS-004). The internet-facing ALB forwarded `/health`, `/metrics`, `/chat`, `/reports/*` and `/api/v1/*` straight to cna-api, which had no authentication, while the web tier was never told where the API was (`CNA_API_INTERNAL_URL` was injected on Azure only). The api target group, listener rule and load-balancer attachment are gone; the api service registers in an ECS Service Connect namespace and the web container reaches it as `http://api:<port>` through a self-referencing security-group rule on the api port. The runtime module generates `CNA_API_TOKEN` (`random_password`, 48 characters) into Secrets Manager `${prefix}/api-token`, and both the api and the web task definitions receive it as a `valueFrom` secret — the core's API rejects every request without `Authorization: Bearer <token>` (except `/health` and `/ready`) and refuses to start in appliance mode without it. **Upgrade order:** apply this release with `210` before letting `230` roll the core images that carry the token check.
- **Workflow inputs no longer reach the shell unquoted** (DEVOPS-001, DEVOPS-009). Every `${{ inputs.* }}`, `${{ github.event.* }}`, `${{ steps.*.outputs.* }}` and `${{ vars.* }}` that was interpolated into a `run:` block in `000`, `210`, `220`, `230` and `330` is bound through `env:` and referenced as a quoted variable; image references and names are additionally allow-listed by pattern. `230-image-update` validates the dispatch payload before it can start `210`: the namespace shape, `sha_tag`, and every `images.*` against `^docker\.io/<DOCKERHUB_NAMESPACE>/cna:(api|web|worker|migrator)-sha-[0-9a-f]{7}$` with the tag equal to `<role>-<sha_tag>`; its job permissions are the minimum each job needs.
- **Terraform plan files are no longer uploaded as artifacts** (DEVOPS-002). A saved plan stores variable values in plaintext, so the `tfplan-*` artifacts carried the database admin password, the Entra client secret, the NextAuth secret and the credential-encryption key for anyone with read access. The plan text goes to the step summary and the apply job re-plans. Past artifacts still need deleting — `REVIEW.md` → R-010.
- **`340-sync-keys` is removed** (DEVOPS-003). It exported every runtime secret into a downloadable `.env` artifact. Secrets stay in Secrets Manager; the console is the read path.
- **Prod-destroying jobs run under the `hub` environment** (DEVOPS-005 / DEVOPS-AWS-002). `330-teardown`'s destroy, drift-cleanup, secret-purge and backend-destroy jobs for `prod` now wait for `hub`'s required reviewers; the typed `DESTROY` confirmation is re-checked before deletion protection is lifted.
- The deploy role's new Cloud Map permission is scoped to the namespace and service lifecycle actions Terraform and ECS Service Connect use, not `servicediscovery:*`.

### Fixed
- **ECS health checks used `curl`, which the core images do not ship** (NET-AWS-001). Every api and web task would have been marked unhealthy and restarted in a loop. The api check is a Python `urllib` probe of `/health`; the web check is a Node `fetch` of `/api/health`.
- **`enable_scale_to_zero` can no longer park the api and web at zero** (NET-AWS-006) — target-tracking cannot scale a service from 0, so dev would have stayed down after its first idle window. The api and web keep `max(1, min_count)`; only the worker honours scale-to-zero.
- **Availability zones derive from the region** (NET-AWS-007). `us-east-1a`/`us-east-1b` were hardcoded; the platform roots now read `data.aws_availability_zones` (overridable with `availability_zones`), and `320-publish-portal` uses the `AWS_REGION` variable.

### Added
- **The destroy guard also protects S3 buckets** (mirror of the Azure appliance's T-101 widening, which added the Foundry account, its model deployment and the storage account there). `210`'s apply job now refuses a plan that would delete or replace an `aws_s3_bucket` on top of the CloudWatch log-group and RDS guard — the artifacts, static-site and edge-log buckets hold data no re-apply brings back.
- **`380 · Project Board`** (`TODO.md` → T-103). Adds every newly opened or reopened issue and pull request — `230`'s `update-available` issues especially — to the one GitHub Project shared with the core and the sibling appliance, with `gh project item-add` (no third-party action to pin). Inert by design until the core's `REVIEW.md` R-012 chooses the token: the job is skipped while the `PROJECT_BOARD_URL` variable is unset and exits with a notice while the `PROJECT_BOARD_TOKEN` secret is unset, never failing an issue or PR over a missing board. Shared workflow — identical in the sibling appliance in the same change set.
- **`210` refuses a plan that would destroy the log store or the database** (mirror of the Azure appliance's `TODO.md` → T-103 guard). Right before each `terraform apply`, the apply job runs `terraform show -json tfplan` through the new shared `scripts/ci/refuse_destructive_plan.py`, which fails the run if any `aws_cloudwatch_log_group` or `aws_db_instance` would be deleted or replaced — history no re-apply brings back. The protected types are the step's `PROTECTED_RESOURCE_TYPES`; a human fixes state or knowingly lifts the guard for one run. Shared script and step, identical to the Azure appliance's.
- **`210` verifies the Bedrock path from inside the environment** (the AWS twin of the Azure appliance's `TODO.md` → T-104). The manifest's `bedrock_model_access` and `bedrock_task_role_inference` were hardcoded `required` and nothing ever flipped them. In `saas` mode the apply job now runs a one-off Fargate task — same cluster, subnets, task role and api image as `cna-api` — executing `scripts/ci/probe_bedrock_path.py`: one Converse call against the model or inference profile the api is configured with. Success passes both; a denial naming the model fails `bedrock_model_access` (the console opt-in `REVIEW.md` R-005 asks for); any other failure leaves it `unverified`. The verdicts enter the manifest through `update_apply_evidence.py` (new optional `AI_PATH_CHECKS` input), and `evaluate_deployment_evidence.py` now refuses `healthy` — and the catalog entry — while any validation check is not `passed` / `not_applicable`, recording the outstanding checks instead. Shared scripts mirrored from the Azure appliance in the same change set.
- **A failing drift check now reaches a person** (`TODO.md` → T-110). `350 · Drift Detection · dev` and `360 · Drift Detection · prod` gain a `report-failure` job that runs when the drift job fails and opens a GitHub issue assigned to the repository owner, deduplicated by exact title so a month of daily failures is one issue that gets staler and louder — each further failure adds a comment — instead of the workflow-author e-mail that a bot-authored schedule sends to nobody. The platform `terraform init` step now classifies the failure: a missing state backend or an empty state is "the dev/prod environment does not exist" (a deleted or never-deployed environment — the five-week silence behind T-110), everything else "the drift check failed"; the two get different issue titles and messages. Drift itself is still a run warning, never an issue. Shared workflow change — mirrored in the Azure appliance in the same change set.
- **Edge access logging** (`TODO.md` → T-111, `terraform-aws:edge-access-logging`). The storage module gains a `<prefix>-logs-<hex>` bucket — SSE-S3, versioned, public access blocked, objects expiring after `log_retention_days`, ACLs left enabled because CloudFront standard logging delivers through the `awslogsdelivery` bucket ACL — and the security module writes CloudFront standard logs to it under `cloudfront/` (cookies excluded) and the WAF web ACL's logs to a us-east-1 CloudWatch log group `aws-waf-logs-<prefix>` with the `cookie` and `authorization` headers redacted, so edge traffic and blocked requests are auditable without a session token ever landing in a log line. Both are behind the roots' `enable_edge_logging` (default `true`); the log group uses the CloudWatch service key because the platform's customer-managed key lives in the deployment region and cannot encrypt a us-east-1 group. New workload outputs `logs_bucket` and `waf_log_group_name`; `330`'s pre-destroy bucket emptying includes the `-logs-` prefix. Cloud-specific Terraform and the AWS-only destroy step — no sibling change.
- **RDS observability options** (T-111, `terraform-aws:rds-observability-options`). The database module takes `performance_insights_enabled` (encrypted with the platform KMS key, 7-day retention by default), `monitoring_interval` (a non-zero value creates the `<prefix>-rds-monitoring` role with `AmazonRDSEnhancedMonitoringRole` and turns enhanced monitoring on) and `iam_database_authentication_enabled`, surfaced on the roots as `db_performance_insights_enabled`, `db_monitoring_interval` and `db_iam_authentication_enabled`. Prod enables Performance Insights and 60-second enhanced monitoring; dev enables neither; IAM authentication is off in both because the application connects with `DATABASE_URL`.
- **The seven operational workflows are real** (`TODO.md` → T-102): `000 · Bootstrap Backend`, `100 · Validate Prerequisites`, `220 · Fast Redeploy`, `330 · Teardown Platform`, `340 · Sync Local Keys`, `350 · Drift Detection · dev` and `360 · Drift Detection · prod` replace their fail-fast scaffolds with the Azure sibling's job shape, step for step, on unchanged inputs. `000` creates and hardens the state bucket (versioning, SSE-KMS, public access blocked), creates the `LockID` lock table, initialises the platform state and confirms the `TFSTATE_*`/`AWS_REGION*` variables — idempotent against what `scripts/Initialize-CnaAwsGitHubSecrets.ps1` already made. `100` checks the secrets and variables the README table lists (`CNA_ENTRA_TENANT_ID` included), probes that the Entra client id still exists, checks Docker Hub pull access, assumes the deploy role and verifies its reader and deploy-write policies, the state backend and Bedrock model access (R-005, the AWS twin of Azure's provider-registration check). `220` rolls one or more ECS services to a new image with `scripts/ci/ecs_update_image.sh` (a new task-definition revision from the current one, tagged so the deploy role's tag-scoped ECS permissions apply, then a forced deployment) and probes `/api/health` through CloudFront. `330` keeps the safety gates, then — AWS having no resource group to delete — runs a real `terraform destroy`, workload then platform, after forgetting the deploy identity in state (so the destroy cannot delete the role it runs as), lifting RDS deletion protection and emptying the versioned buckets; it clears both state objects, previews and optionally deletes tagged leftovers, force-deletes secrets still in their recovery window (the twin of Azure's soft-delete purge) and, on request, removes the backend — refusing while the other environment still has state in the shared bucket. `340` reads the four Secrets Manager secrets plus the Bedrock contract values from the api task definition into a 1-day `.env` artifact; there is no firewall window to open or close. `350`/`360` plan both roots with `-detailed-exitcode` against the images and `ai_mode` recorded in the release catalog, warn on drift, and — unlike the Azure versions — fail when the plan itself errors; `350`'s daily schedule is present but commented out until dev has been deployed once. Authored and validated (YAML, every `run` block under `bash -n`, yamllint, every action SHA-pinned, `terraform validate`), not yet run.
